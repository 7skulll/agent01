# RAG 流程与开发顺序

RAG 分为资料入库与在线问答两条链路。文档向量通常在导入时计算，提问时计算问题向量；不会每次把全部文档交给 LLM。

## 一、资料入库（下一阶段）

1. **接收与标识**：接收文件，记录知识库 ID、文件 ID、原文件名和内容哈希；后续避免重复入库并支持更新清理。
2. **格式解析**：不同解析器将 PDF、MD、Word、表格转为文本结构。PDF 提取文本层，扫描件无可用文本时明确失败，不伪装解析成功。旧 `.doc` 需要转换工具或专用解析器，不能直接当 `.docx` 读取。表格保留表头与相邻内容，避免值失去语义。
3. **清洗与切片**：清理噪声，优先尊重标题、段落与表格结构；长内容切成有重叠的片段，保留知识库、文件、页码等元数据。当前只实现通用字符切片，参数是起始值，需要根据样本调整。
4. **向量化**：调用 Qwen Embedding API，将片段转换为向量。批量请求、限流、重试与失败记录在真实接入时实现。文档和查询使用相同模型及向量维度。
5. **索引保存**：保存片段、元数据与向量，并建立关键词索引。存储技术尚未决定；替换 Embedding 模型通常需要重建向量索引。

## 二、在线问答

1. **接收问题和知识库范围**：校验问题与历史消息，限定目标知识库。
2. **理解追问**：例如先问“年假如何申请”，再问“需要提前几天”，将追问改写为“年假申请需要提前几天”。历史只用于理解指代，不作为知识库证据。
3. **问题向量化**：用相同 Embedding 模型编码检索问题。
4. **混合召回（计划）**：向量检索寻找语义相近片段；关键词检索补充产品名、编号、专有名词等精确线索。两路都必须在目标知识库内搜索。
5. **融合与排序（计划）**：去重并合并候选结果，评估融合方式；需要时接入 Rerank，对候选重新排序。先看评估效果和耗时，再决定是否启用，不照搬 RAGFlow 的参数。
6. **上下文组织**：选择高质量片段，在模型上下文预算内组织资料。当前按 `top_k` 限制数量，后续增加 token 预算与证据质量判断。检索分数不是答案正确率，阈值要通过样本校准。
7. **生成回答**：LangChain 提示词和模型链调用 DeepSeek，要求依据资料回答。没有有效片段时直接回复资料不足；有片段也可能不包含答案，需要评估拒答质量。
8. **输出与验证**：第一版返回答案和回答状态，不展示引用；内部保留文件标识，为检索调试与后续引用功能准备。会话持久化后续实现。

## 三、如何借鉴 RAGFlow

已查看本地 `../ragflow-main/rag/nlp/search.py`：`Dealer.search` 构造全文与稠密向量查询及融合表达式，`Dealer.retrieval` 组织召回、排序和阈值过滤；存在 `rerank`、`rerank_by_model` 等排序路径，不同存储后端处理方式有所区别。

借鉴的是“多路召回 → 融合 → 排序 → 过滤 → 上下文”的思路。暂不加入 GraphRAG、Agent、RAPTOR 或复杂工作流，先验证普通信息检索链路。

## 四、开发顺序与测试

1. **当前：框架**。配置、API、LangChain 切片和问答编排；离线验证参数校验、未就绪状态、追问改写、知识库范围、无证据处理和元数据保留。
2. **解析入库**。实现文件读取、格式解析、清洗、结构感知切片；测试多格式、空文件、扫描 PDF、中文、表格与失败反馈。
3. **基础检索**。接入 Qwen、持久化存储与向量检索，验证导入 → 检索，以及知识库隔离；加入关键词索引和融合后比较命中率。
4. **真实问答**。接入 DeepSeek 与追问链，增加上下文预算、异常处理和 API 超时；真实文档验证直接提问、追问、资料不足。
5. **检索优化**。建立固定问题集，对比切片参数、混合召回与 Rerank，记录命中率、回答正确率、拒答质量、延迟和费用。

组件依据：[LangChain 包职责](https://reference.langchain.com/python/langchain/overview)、[切片组件](https://reference.langchain.com/python/langchain-text-splitters)、[Embedding 接口](https://docs.langchain.com/oss/python/integrations/embeddings)、[FastAPI 生命周期](https://fastapi.tiangolo.com/advanced/events/)。
